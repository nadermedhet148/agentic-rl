How the agent remembers

Before every planning step, the agent pulls three kinds of memory into the planner's prompt. Two of them are filled by your feedback, and one is filled by the conversation itself. Everything lives in one SQLite file.

The fourth tier

Procedural memory is the bandit's learned weights (one A/b matrix pair per arm). It never enters the prompt. It is saved to the policy_state table after every update and reloaded on boot, so the agent keeps what it learned across restarts.

01 · Finding memory

Which past corrections are "similar"?

There are no embeddings here. Retrieval is lexical: SQLite FTS5 with bm25 ranking, plus a filter in Python that FTS5 can't express on its own. The same helpers in core/text.py search both past corrections and existing rules.

  1. Tokenize

    Split on letters and digits, lowercase, drop tokens shorter than 2 characters.

  2. Drop stopwords

    Request filler like fetch, get, please, the would match everything.

  3. FTS5 OR query

    Each token is quoted and OR-ed together. This favours recall; anything sharing one token comes back.

  4. Rank with bm25

    Columns weighted request 1.0, correction 0.5, hosts 3.0. A shared host outranks shared words.

  5. Min-overlap filter

    Keep a row only if its request shares ≥ 2 tokens with yours (≥ 1 if your query has a single token). Top 5 go to the prompt.

02 · The memory itself

Corrections become standing rules

A raw correction only helps when a future request looks similar. So every ✏️ correction is also distilled by an LLM into one general, imperative rule. All active rules are shown to the planner on every request, whatever it asks, sorted by how often they've been confirmed.

A rule on file

text
always send Content-Type: application/json to httpbin.org
capability
http_call, or empty to apply everywhere
support_count
how many corrections said the same thing
source_episode_ids
the episodes it came from
superseded_by
the rule that replaced it, if any
active
only active rules reach the prompt

How the Consolidator decides

  1. Gather candidatesRules whose text overlaps the correction (same FTS search), plus active rules for each capability the episode used.
  2. Ask the DistillerIt sees the request, the actions taken, the correction and the candidates with their ids. It returns a rule and, optionally, a match or supersede id.
  3. Apply one outcomeSame meaning: bump support_count. Opposite meaning: add the new rule and deactivate the old one. Otherwise: add a new rule.

Why a guard on ids

An LLM can name a rule id it was never shown. The Consolidator only accepts a match or supersede id that was in the candidate list it sent. Anything else is ignored, and the correction is saved as a new rule. That way a made-up id can't bump or retire the wrong rule.

You can also add a rule directly with POST /memories (no distilling) and retire one with DELETE /memories/{id}. The UI shows them in the Rules panel.

03 · The conversation store

Sessions remember what you just said

Rules and corrections are permanent and shared across conversations. A session is different. You start and end it yourself, and it only holds this conversation's own turns, so "now make that a PDF" knows what that is. To keep the prompt from growing forever, every 5 turns the oldest unsummarized turns are folded into a rolling summary.

The summarizer's brief

Keep concrete facts, filenames, URLs, numbers, and what was generated or scheduled. Drop filler. Stay under about 200 words, keeping the newest details when space runs out.

If summarizing fails

The user already has their answer, so a summarizer error never fails the turn. turn_count still goes up, and the summary is retried after the next turn.

04 · Putting it together

The order the planner reads it in

Each section renders to nothing when it's empty, so a session-less request with no history has a much shorter prompt. Rules and corrections come last, right before the planner writes its candidates.

  1. Conversation so far in this sessionSummary of earlier turns, then recent turns verbatim.
  2. Steps completed so farThis episode's own plan, act and observe loop.
  3. Standing rules from this user (binding, always apply)Up to 50 active rules, most supported first.
  4. Corrections from past similar requestsUp to 5, from the ranked search.
